# Decode throughput after the bounded AVX2 merge

**Refresh the Rust–C profile on the landed decoder, then tackle match reconstruction.** The widest measured win in this round came from doing less work in the mixed-bitmap merge, not from moving file reads to workers. The historic multi-gigabyte throughput deficit on the 12-frame bundle did not reproduce, but eight-worker Rust still uses more CPU per GB. The highest-upside next bet is a bounds-proven SPL16 bulk loop if the new profile supports it. The most developed smaller candidate is the compact Huffman table: retest it on current code, including small blocks and Wasm, rather than reject it solely for being below 5% on one workload.

This closes the experiments tracked from [the original `next0` shortlist](next0.sol.md), with earlier work included where it explains the baseline. `0cdb6270` is the last measurement checkpoint; `7209e2d9` is the latest timed code pin (merge `45415859` plus a test-only lint fix). Landed here means committed in the tree. `main` was then pushed to Tangled at `809b5faa`, not to GitHub `origin`, so these commit IDs are published. The [commit account](commit-account0.glm54.md) speaks to every commit in the pass and holds the deferred long-form messages. No new code or measurements were made for this handoff.

## Where we stand

These are the **direct landed Rust/C pairs**, not ratios computed from separate parent comparisons. Values separated by `/` are the two series' absolute medians; paired changes and intervals are in the [landed report](../../doc/profiling/bitmap-merge-landed0.sol.md#direct-cli-pairs). Throughput is decimal GB/s of verified plaintext.

| Fixed C7 input | Workers | Landed Rust GB/s | Pinned C GB/s | What the paired results establish |
| --- | ---: | ---: | ---: | --- |
| `single`, one long frame | 1 | 1.79 / 1.80 | 1.81 / 1.80 | No resolved difference on one pinned core; not a parity proof. |
| `single`, one long frame | 8 | 8.78 / 8.31 | 9.46 / 8.70 | Rust throughput −7.5% / −2.9% vs C (second unresolved); Rust used 18–20% more CPU/GB. |

| `sao` | 1 | 0.89 / 0.90 | 0.76 / 0.75 | Rust +18.1% / +19.4% vs C. |

The [older 8.45 vs 2.76 GB/s result](../../doc/profiling/silesia-status-20261120.md#decode-throughput-by-worker-count) was C vs Rust on **concat before worker reuse**, with no fixed placement on a busy host. The [same original concat, rerun after the merge](../../doc/profiling/bitmap-merge-landed0.sol.md#follow-up-the-original-12-frame-concat) did not reproduce that gap. `concat` and `single` decode to the same 211,938,580 bytes but are **different compressed inputs**. Do not compare between them as if only the frame boundaries changed.

Latest W1 pins both CLIs and all their threads to CPU 3; W8 uses CPUs 0–7 on the Ryzen 5800X. Earlier W1 runs let C's driver threads use extra cores; e.g. pre-merge C was 55–58% faster than then-current Rust on `single` with a wider affinity mask. **We have not rerun that wide-mask W1 comparison on the landed merge.** Likewise, the old one-core **2.95 vs 1.94 cycles per verified plaintext byte** came from resident replay *before* width six and the new merge, not from the current decoder. CLI W1 on one core does not settle the kernel-only gap.

## What did not land

| Trial | Disposition and why |
| --- | --- |
| SPL16 32-byte snapshot for 20–32 byte extensions (`next0` #1) | [Rejected](../../doc/profiling/decode-next0.sol.md#initial-checked-replay). About 4.7% of `single` tokens qualified, but the old 64-byte copy already inlined. The split added instructions and checked cycles moved +0.7% / +1.1%. No CLI run justified; do not try a ladder of copy widths. |
| Worker-side positioned reads (`next0` #2) | [Rejected for W8](../../doc/profiling/decode-positioned0.sol.md#clean-gate-no-qualifying-speedup). Correct scratch prototype, no production selector. Coordinator admission CPU dropped by ~96%, but `single` wall moved +5.1% / +2.0% (slower; second unresolved); concat moved +1.0% / −4.4%, both unresolved against zero. The 10% target was excluded on both long-frame runs; the CPU ceiling and pipe nonregression were unresolved. It leaves the serial path unchanged. Moving work out of the coordinator is not removing it from the process. |
| Distance-one fill (`next0` #4) | [Screened out, never built](../../doc/profiling/decode-next0.sol.md#spl16-eligibility): 0.054% of `single` tokens, 0.74% of its output bytes, and 32 matches in `sao`. Not a general rejection of overlap kernels; choose them by weighted cost. |
| Compact inline Huffman tables | [Implemented, verified, not landed](../../doc/profiling/decode-compact0.sol.md). Kept the old dictionary/encoder paths and the same unpack/gather kernels. `single` literals saved 7–8%, tokens 20–21%, checked instructions/byte 3.35%, but checked cycles saved 5.3% / 3.5% and only 0.8% on the targeted repeat. W1 gained 5.2% / 3.4% and 4.9% on the repeat; `mozilla` gained about 4.5% twice. One entropy-heavy native scalar 4 KiB fixture gained 68–71%. Missed the original combined 5% gate—not a failed mechanism. **Still worth revisiting**, especially small blocks; no Wasm whole-call data and no current-parent comparison. |
| Earlier paired eight-output AVX2 shuffle (`next0` #5 background) | [Rejected](../../doc/profiling/pivco-avx2-merge0.sol.md). Lane construction, checks and spills survived; long literals used 12.5% more cycles and checked blocks 6.5% more. Keep the oracle. The landed 32-output merge instead uses two complete 16-output lanes and one full-width store. |
| BMI2 `PDEP` versus 32-output AVX2 | [Drop `PDEP` on the measured Zen 3](../../doc/profiling/bitmap-merge-race0.sol.md#kernel-discriminator). Deposit did beat old Rust (~23–25% fewer gather cycles) but lost directly to AVX2; no reason for the extra path and CPU allowlist. BMI2 support alone is not a speed guarantee (notably Zen 2). The initial AVX2 version's direct scalar suffix also failed on right-skewed runs; only the revised eight-output suffix landed. The revised short-literal microcase was 3.09% slower, with no resolved loss in either 4 KiB CLI control. |
| Prior alternating scratch / traversal queue | Keep as negative evidence: [alternating buffers](../../doc/profiling/pivco-scratch.md) eliminated copy-back but did not win serially and hurt a WIT workload; [FIFO reuse experiment](../../doc/profiling/pivco-queue.md) removed most growth/allocation events without clearing its elapsed target. Fewer copies or allocations alone are not acceptance evidence. |

## Next iterations, in order

1. **Get a new paired scorecard and profile before ranking the residue.** Use the current Rust tree and the same C `5719a96f` reference. Measure `single`, `concat`, `mozilla`, and `sao` at W1/W8; include C and Rust `-T1`/`--threads 1` on **both** one core and the same wider core mask as separate questions. Record child CPU/GB and observed active threads. Add a truly one-thread checksum-on block replay and symbol attribution on the original sections. The [older attribution](../../doc/profiling/decode-gap0.sol.md#attribution-distinguish-traffic-from-hot-loops) assigned about 38% of excess checked-block cycles to reconstruction, 26% to gather, and 19% to unpack; it guided two successful changes, but those shares are stale. Don't infer the present breakdown by subtracting isolated kernel wins. For broader claims, rerun the [full Silesia matrix](../../doc/profiling/README.md#compare-compression-and-fixed-archive-cli-decode), including C7 and Rust-produced Dense/Split archives, once the narrow tests are stable. For I/O claims add distinct real-file and actual-pipe cases, not a reinterpretation of `/dev/null` throughput.
2. **Bold codec bet: open up the SPL16 bulk interior.** Census why the current two-token batch exits (extended literal/match, actual overlap, insufficient initialized room, dictionary/history, tail) and attach the samples to those classes. Use `single`, match-heavy `mozilla`/`webster`, and `sao` with zero extended matches. If ordinary tokens dominate, try hoisting checks over a proven interior with initialized output room and enough prior history to cover all representable offsets; keep the checked terminal/dictionary path. If overlap owns the residual instead, pick one common *measured* distance class. C's wider bulk loop is a useful reference, not permission to rely on its scratch padding. Compare reconstructed bytes to the independent bytewise oracle, then checked blocks and W1. No bundle of entropy and LZ changes.
3. **Low-risk unpack follow-up: test width five if it still shows up.** It was the next-largest sampled flat width before width six (4.97M literal symbols on `single`, 21% of flat samples). Reuse the saved-run method and exact-bit oracle, use bounded wide groups with the existing tail, and keep lookup operations appropriate to each ISA. Confirm relevance on the current profile before specializing more widths. An isolated win is valuable but not a wall claim. Independently measure the ARM64 NEON kernel on hardware before adding further ARM optimizations; `TBL2` merge is a plausible native candidate, not a measured requirement. RVV can wait for hardware and a demonstrated narrow kernel; no need to build an entire Fearless backend first.
4. **Reopen compact tables as a small-block/serial candidate, not as a rewrite budget.** Rebase [the decode-only patch](../../doc/profiling/decode-compact-sol-data/trial.patch) onto the current decoder, preserving the landed kernels, encoder and cached dictionary path. Check current C7 W1/checked blocks, entropy-heavy and sparse/RAW 4 KiB inputs, native scalar and whole-call Wasm with the same Wasmtime host. Track bounded stack/scratch and binary/component size. A repeatable few-percent improvement with clean controls can justify it; the huge result on one 4 KiB fixture alone cannot.
5. **Only reopen merge scheduling or input if the new data points there.** If gather remains expensive after the landed AVX2 kernel, [fusing flat/leaf children with their parent gather](bitmap-merge0.astra.md#ranked-alternatives) is materially different from alternating scratch: it can avoid creating child streams and a copy-back at selected nodes. The untimed census put about 10% of literal and 17% of token gather bytes at eligible terminal parents before a length gate; start with common width pairs, not a general fusion scheduler. If W8 wall remains a priority, first measure interior worker idle/reader CPU on the **new** decoder and on the intended sink. Neither another positioned-read rewrite nor a bigger queue is justified by the old coordinator CPU savings alone.

## How to compare and decide

- **Freeze bytes and revisions.** Reuse the [fixture manifest](../../doc/profiling/decode-pool-data/fixture-manifest.json) and [preparation recipe](../../doc/profiling/decode-pool.md#method-and-evidence). `single` is a 405-block C7 frame; `concat` is the original 411-block, 12-frame bundle. Keep fixed bytes, checksums, format validation, worker count and slot budget. Clean locked portable Release Rust parent A and candidate B; pinned native Release C as a *separate* pair, not the Rust baseline. Keep `target-cpu=native`, diagnostics, Tracy and ledger out of shipping timings or label them as distinct comparisons.
- **Follow the effect all the way out.** Saved run (cycles/instructions per gathered byte or decoded symbol) → section replay (same original tables and bits) → checksum-verified block replay (cycles/instructions per plaintext byte, thread CPU) → CLI (wall throughput, whole-child CPU/GB). Report padding/validation, cache and output contracts on both sides, especially when reusing C's padded worker probe. Preflight verifies lengths and hashes through EOF and rejects altered checksums and invalid tables. Timed replay checks fingerprints. Keep small/RAW, skew/short, dictionary and no-default controls; for cross-platform code use [QEMU correctness](../../doc/testing/linux-qemu.md) and available Wasm smoke. Emulation cannot establish throughput.
- **Use direct pairs, not remembered GB/s.** Hold `.test-agent/zxc-perf.lock`; warm and pin both arms. Two independent shuffled series of 24 adjacent balanced AB/BA pairs, with interleaved same-A controls for the cases/placement being judged. Record physical cores, SMT siblings, governor/boost, load, toolchains/hashes, raw order and per-series estimates/intervals. Reject multiplexed PMU counts. A/A quantifies noise; do not subtract it. An interval crossing zero is unresolved, not parity; a quieter targeted repeat is useful once if it changes the decision. Do not mix old absolute medians, single vs concat, pinned-one-core vs wide-mask W1, or C and Rust percentages with different denominators.
- **Ship useful improvements with the right claim.** A fixed 5% is not a minimum for accepting a real, low-risk gain. The width-six example is a verified section win with lower checked instructions; the mixed gather is a verified whole-decode win. For a complex change require credible evidence on the actual workload and no meaningful control loss; don't waive correctness or promote a noisy favorable point estimate. Keep independent patches and retest on the landed baseline rather than summing their gains.

Start a fresh comparison with the [landed CLI recipe](../../doc/profiling/bitmap-merge-landed0.sol.md#conditions-and-verification), or reassemble the [checked replay and profiling setup](../../doc/profiling/decode-replay0.sol.md#reproduce) at a new Rust pin. The [profiling guide](../../doc/profiling/README.md) indexes the raw measurements, archived trial patches, and diagnostics. `.test-agent/` holds local scratch and is not required to retain the recorded results.
