# Deposit the child bytes directly on Zen 3

**Prototype BMI2 byte deposit first on the Ryzen 5800X.** One 2 KiB table turns eight branch bits into a 64-bit mask with whole bytes selected. Two `PDEP`s and one OR place the next left and right bytes directly in output order. Unroll four words per 32 outputs. There is no SIMD lane construction, shuffle-control assembly, blend or partial-lane store. Race it against the pinned C 32-output AVX2 kernel on the *same mixed runs*. If C wins, port that kernel with a Rust bounds proof. Both bets are better than spending another iteration on two eight-output shuffles.

## The size of the wager

On original C7 `single` literals, the [cycle attribution](../../doc/profiling/decode-gap0.sol.md) assigns **2.517 Rust vs 1.312 C cycles per decoded symbol** to mixed gather: 1.205 of the 2.508-cycle literal gap. Copy-back is separately 0.197. On 405 checksum-verified blocks the corresponding gather estimates are **0.569 vs 0.302 cycles per plaintext byte**; the whole gap is 1.015. Improving this one kernel matters even if flat unpack and match reconstruction stay put.

The [run census](../../doc/profiling/decode-replay-data/decode-gap0-sol.tar.xz) counts **92,741,351 gathered bytes / 34,911,224 emitted literals = 2.66** passes through mixed nodes per literal. Of 4,157 mixed runs only 10 are shorter than 32; **92,731,023 bytes** are in runs ≥128. Tokens add 30,483,177 gathered bytes in 5,112 runs; 52 runs are shorter than 32. Dividing the literal attribution by the observed gather volume puts Rust at roughly **0.95 vs C 0.49 cycles per gathered byte**. These are sampled costs in section decode, not isolated kernel timings. Length does not tell us minority counts, mask order, or when one child nears exhaustion. The count of bytes, cache footprint, and theoretical instruction throughput predict neither checked-block nor CLI speed.

The [two-group AVX2 trial](../../doc/profiling/pivco-avx2-merge0.sol.md) emitted a 256-bit shuffle but had to assemble two 8+8 inputs, check their windows, and repack two half-empty outputs; spills and reloads survived in the timed binary. Long literals took **12.5% more cycles**, checked blocks 6.5% more. [Alternating buffers](../../doc/profiling/pivco-scratch.md) removed every copy-back byte but failed to win serially and slowed one WIT workload 11–13%. Keep the bottom-up layout and copy-back for the kernel comparison. The opportunity is cheaper **selection on each visit**.

**The exact-window path already covers 99.73% of literal gather volume.** I counted actual eligible 32-output tiles in a new, untimed walk of the original bitmaps. With the proposed `n>=128` entry gate:

| `single` | All mixed bytes | Exact 32-byte slabs, no guard | With initialized guard | Additional coverage |
| --- | ---: | ---: | ---: | ---: |
| Literals | 92,741,351 | 92,492,192 (99.73%) | 92,667,776 | 0.19 percentage points |
| Tokens | 30,483,177 | 30,155,840 (98.93%) | 30,382,080 | 0.74 percentage points |

To reproduce, use `runs` in the bundled `shapes.py` and `run/single-{lit,tok}.idx` on the manifest archive (SHA-256 `32608ad174575d9e7563bcc9f535a94ba32033480c34deb6d9cbe972c40f0843`). At the mixed-node yield inspect the original `run`: for `n>=128`, start `rleft=ones`; for each full 32-output group, stop if `rleft<32`, otherwise add 32 and subtract the population of its four bitmap bytes from `rleft`. The guarded count is `32*floor(n/32)` per eligible run. The equivalent reverse walk starts with the masked partial group's population, adds preceding full groups until the suffix has ≥32 ones, then credits all groups through that start. **Skip padding in the first prototype.** Any large win from padding here would have to come mainly from cheaper code or disproportionately expensive tail work, not much more bulk coverage.

## First prototype: four integer merges in flight

Let `L | R` be the already decoded stable child lists in one initialized region. A zero takes the next L byte; a one takes the next R byte, LSB first. Define `M[b] = Σ (((b >> i) & 1) * 0xff_u64 << (8*i))` for `i=0..7` (inclusive). Store `[u64;256]`: **2,048 B**, no second table, no count field. Keep the wire bits packed. `PDEP(y, m)` deposits the *low* bits of `y` in increasing set-bit positions of `m`, zero elsewhere. A set byte in `m` admits exactly eight consecutive source bits, so order *within* and *between* selected bytes is preserved. `PDEP(x,!m)` fills exactly the complementary bytes. E.g. `b=0x4d` emits `R0 L0 R1 R2 L1 L2 R3 L3`. This operation works on arbitrary symbol values; it does not encode a symbol as one bit.

```text
o = l = r = 0                               # logical output, left, right cursors
while n - o >= 32 and physical_windows_fit(l, nl + r):
    A, B = two readable 32-byte views at l and nl+r in the source arena
    w = load_le32(bitmap[o/8 .. o/8+4])
    for k in 0..4:                          # 0,1,2,3; fully unrolled
        p = popcnt(low 8*k bits of w)       # p[0]=0; independent of earlier loads
        m = M[(w >> (8*k)) & 255]
        x = load_le64(A[8*k-p ..][0..8]); y = load_le64(B[p ..][0..8])
        store_le64(dst[o+8*k ..][0..8], pdep(x, ~m) | pdep(y, m))
    q = popcnt(w); l += 32-q; r += q; o += 32
finish_from_cursors(region, dst[o..], bitmap[o/8..], l, nl+r)
```

Do the prefix counts for low 8, 16 and 24 bits and the full 32 in parallel from `w`, rather than four serial updates dependent on table loads. The only loop-carried right-position update is `r += popcnt(w)`; `l` can equivalently be derived from `o-r`. Inspect which formulation actually retires less work. Start the new dispatch at `n>=128`; shorter nodes keep today's path. Allow a long run with a tiny child to use the new kernel if its **physical** views fit. Whole uniform nodes still skip gathering entirely.

**Why this can beat C on this CPU.** The [register PDEP measurements](https://uops.info/html-instr/PDEP_R64_R64_R64.html) give Zen 3 one per cycle, latency three. Independent deposits can overlap; eight deposits per 32 outputs imply an instruction-resource floor of **0.25 cycles/gathered byte** from PDEP alone. There is room between that and the observed ~0.95; there is also room to *lose* to C's ~0.49. Eight child loads, four mask loads, four stores, complements/ORs, prefix counts and address arithmetic per 32 are real. A frontend, load-port or cursor bottleneck could dominate. The test is whether avoiding C's control assembly and Rust's current range checks buys more than the extra word-level operations cost.

### Bounds that can survive code generation

1. **First arm: no allocation change.** Supply the whole initialized source interval, not two provenance-limited child slices. At a tile boundary, `0 <= l <= nl <= nl+r <= n`. `n-(nl+r) >= 32` suffices to make **both** 32-byte slabs physically readable. Within either slab a group starts at `0..=8*k <=24`, hence its entire eight-byte load fits. A logical L load may overlap R; deposit ignores all bytes beyond the number of zeros/ones in that group. Exact child consumption follows from the previously counted bitmap. Writes are to a nonaliasing 32-byte destination chunk. Use checked slice-to-array references and little-endian conversions; if LLVM needs help, indexing a `[u8;32]` at `min(offset,24)` makes the inner load total in safe Rust, and is the identity on valid offsets. Inspect the cost: four pairs of bounds branches or clamps per tile are *not* free. Allocation capacity, neighboring allocations, and `MaybeUninit` are never evidence for readability.
2. **Exact suffix.** On a failed slab proof or fewer than 32 outputs, pass the two current cursors to the existing exact cursor (optionally the existing bounded eight-byte step first). Do not call `gather` as if the unconsumed lists were still adjacent. `o` is byte-aligned in the bitmap; the last 0–7 symbols ignore the unused high bits. A short R can leave a *long* suffix even if L is huge: count the bytes actually taking this exit, separately by skew direction. This proof is intentionally a measurable first choice, not an assumption that 92.73M bytes qualify.
3. **If the physical exit is costly: one initialized guard per source arena.** In a separate arm make the readable source prefix `count + 32` for the slab implementation; a final cursor can equal `count` while the other side still has work. Thus **32**, not 31, bytes suffice for *any* slab at any node. Only eight extra bytes are needed for individual unchecked-width word loads under a node-wide cursor proof; eight are *not* enough to take `&[u8;32]` at an exhausted cursor. Similarly the C-like four 16-byte loads only need **16** bytes beyond the physical node end, even if one side is exhausted. If using a wider checked slab to prove those loads, budget its actual width instead. Read from an immutable initialized `output[start..start+n+guard]`, gather to disjoint `scratch[..n]`, end the borrow, then copy exactly `n` back; neighboring initialized nodes supply the interior slack. The guard need not be zero for correctness; initialize it by checked `reserve_exact`/`resize` on growth, never `set_len` over capacity. Return only `[..count]`. No guard on bitmap, wire, scratch destination or returned plaintext. Do not allocate or copy two padded children per node.

The [block retention limits](../../crates/codec/src/block.rs) release a literal/token Vec whose capacity exceeds `limit` / `limit/5`. A padded-arm trial must account for those **physical** bounds (`checked_add(guard)` on eligible source buffers, logical ceilings unchanged), growth, ledger and reuse across small/large frames; or decline padding when it would exceed the existing cap and take the exact fallback. Otherwise a maximum-size section can reallocate on the next block and erase the gain. Two source Vecs can each retain the added guard per worker. An even smaller experiment borrows already-initialized tail bytes when `output.len()` permits; disclose its coverage on cold starts. Extra room establishes legality, not removal of bounds checks by LLVM.

The [codec forbids unsafe code](../../crates/codec/src/lib.rs). The pinned `fearless_simd::kernel!` `Avx2` token enables BMI2 and POPCNT on x86; use the safe register `_pdep_u64` intrinsic inside that target-feature body on **x86-64**, plus ordinary checked byte loads/stores. Dispatch once per eligible run or cache the CPU decision for the section. Inspect the **portable Release** executable, not just a `target-cpu=native` listing. Direct unsafe unaligned loads/stores are useful as a *scratch-only ceiling* if checked code spills/tests every window: bound the loop once with the proved spans, compare otherwise identical arithmetic, and include the exact tail. They are not a reason to remove `forbid(unsafe_code)`. If such a backend is ever proposed for production, its safe API must prove all physical bounds itself (or carry a private validated bitmap/count witness); it cannot trust public integer counts for memory safety. First look for safe codegen within the proved slabs.

## Ranked alternatives

1. **BMI2 deposit on known fast-PDEP x86-64** as above. ISA support is a legality test, *not* a speed test: the same instruction measures **19 cycles reciprocal throughput on Zen 2**. Benchmark-force on the 5800X first; if promoted, cache a conservative measured CPU family/model allowlist **and** the feature proof. Other BMI2 hosts stay on the existing path until measured; no CPUID in the inner loop. No reason to enable this on every AVX2 processor.
2. **Strongest general AVX2 alternative: C's full 32 outputs, with four 16-byte child loads.** Use two 16-output lanes A/B; the second starts at `l+16-pcA, r+pcA`, where `pcA=popcnt(low16(w))`. Construct each lane's first eight selectors from `I[b0]` and second eight from `J[popcnt(b0)][b1]`. `I` selects `rank0` or `16+rank1`; `J` adds the preceding half's `8-popcnt(b0)` or `popcnt(b0)` to the respective rank. Sizes `256*8 + 9*256*8 = 20,480 B`. Join the two lanes, do `vpshufb(L,ix)`, `vpshufb(R,ix)`, blend on bit 4 shifted into each sign bit (`vpsllw 3`), **one full 32-byte store**. Each shuffle implicitly takes the low four selector bits within its lane. The high-lane loads do not start blindly at `+16`. The same 32-byte slab proof works: high-lane displacement ≤16 plus a 16-byte load. Follow with the exact tail. This is the [actual pinned inner loop](https://github.com/hellobertrand/zxc/blob/5719a96f778226868b29dba621a8c4e302b74d7c/src/lib/zxc_huffman.c#L1441-L1475); C also alternates level buffers and assumes source slack. It amortizes loads and stores better than deposit but pays for indexed rows and lane assembly. Compare under *like* initialized spans before blaming the ISA. Safe `core::arch` arithmetic in `kernel!`, array loads/conversions, and disassembly before considering any audited raw-load backend. Do not expand the LUT to `65536*16` (1 MiB) just to save the second selector lookup.
3. **If both are still expensive: remove a merge at the producer.** Census a mixed parent with two terminal **flat/leaf** children. It has no dependency on previously gathered byte lists: its child inputs are immutable wire runs and symbol tables. A fused tile consumes the next `32-popcnt(w)` and `popcnt(w)` codes at the two child bit cursors, maps them, merges in registers and writes *directly* to the parent's output interval. Leaf children broadcast; for a leaf and a one-bit pair, deposit the pair's next packed code bits into the parent's pair-selected positions with a single **bit-level** PDEP per ≤64 parent symbols, then expand two bitmaps to three possible symbols. Avoid materializing both child lists, the intermediate gathered scratch **and** that parent's copy-back. This changes the schedule, unlike copying the same gathers to alternating buffers. Record disjoint eligible bytes **by width pair**, not just the number of leaves: the literal census bounds leaf+flat-1 alone by `(1.84M + 1.08M)/92.74M < 3.2%` of gather volume. Wider flats and two-flat parents are the real question. Arbitrary bit offsets, bounded unaligned code windows, live registers and table pressure may kill it. Advance only if census and replay of those exact motifs justify a separate integration trial. Keep original breadth-first sizing/validation; only defer emission for proven terminals. Do not bundle it with the width-six trial.
4. **Defer expanded per-node merge plans and repacking the source.** Caching a mask and prefix per eight outputs during popcount can shorten the address chain, but even one `u64` per byte of bitmap expands 11.59 MB of `single` literal masks to ~92.7 MB of plan data over a pass; each plan is normally used once. If dependencies really dominate, sample a prefix only per 128 outputs (one `u32` = 1/32 plan byte per gathered byte) to start independent tiles, charging construction and reads. Physically packing `L-group | R-group` for every tile makes one-source shuffles possible, but a standalone repack first reads and writes the very bytes we wanted to save. Price this only with a producer that emits the layout directly and an oracle for uniform ancestors. A bigger table, more slack or fewer counted copies by themselves are not results.

The same untimed walk found **9,469,977 literal (10.21%) and 5,180,985 token (17.00%)** gather bytes at parents eligible for #3, before a length gate. Count a mixed node's `n` once if both direct children are leaves or have a known positive perfect height in `shapes.py`; label a leaf width zero. No such parent contains another eligible parent. The largest literal pair was widths `(2,3)` at 1,669,218 bytes, followed by `(leaf,3)` at 1,602,009; `(2,3)` alone covers 2,458,345 token bytes. That identifies a concrete second-wave fusion probe rather than assuming every byte can avoid its merge.

**Other ISAs:** On actual AVX-512 **VBMI2** hardware my first choice changes: 64 bitmap bits are the byte-lane mask. `v = expandload(zero, ~w, L+l); v = expandload(v, w, R+r); store64(v)` consumes exactly `64-popcnt(w)` and `popcnt(w)` bytes; zero-mask accesses consume none. Two byte expand-loads, no selector table or source guard, full groups and an exact suffix. Require the feature set for the exact instructions and OS vector state; AVX-512F or VBMI alone is insufficient. The 5800X cannot measure this. On AArch64 NEON, `TBL2` indexes two 16-byte registers directly for 16 outputs, using the same `I/J` rows; one table lookup replaces x86's two shuffles and blend. Compare with today's NEON on real hardware, with the same 16-byte physical guard or interior+suffix proof; two-register lookup and popcount costs differ by core. On Wasm keep explicit strict SIMD128 / relaxed SIMD components on today's tested indices 0–15, and the unflagged component on its scalar cursor. A larger table can affect whole-component performance even on RAW. Native `--no-default-features`/no `merge-simd` keeps the table/cursor, SSE2 fallback and other unselected tiers keep their present dispatch. No new target features for an entire portable executable or default Wasm artifact.

## Handoff: a race with a stop condition

1. **Freeze the work.** Use the [fixture manifest](../../doc/profiling/decode-pool-data/fixture-manifest.json), `single` literal **and** token section indexes in the census bundle and the retained decoder as A. During an untimed reference walk, capture each mixed node immediately before gather: `(section, node, start, n, nl, original mask bytes, L|R, expected output)`. Hash captures, retain order/offsets; check aggregate counts against `shapes.jsonl`. Stratify by length, minority fraction (both directions), homogeneous groups and bytes in bulk vs exact suffix. Replay all nodes in their original frequencies; don't create a balanced-only hot table benchmark. Keep `mozilla` and sparse `sao` sections; the [short/skew benchmark](../../crates/codec/benches/pivco_merge.rs) is a stress control, not the main distribution.
2. **Prove bytes before timing.** The [current tests](../../crates/codec/src/entropy/tests.rs) independently stable-partition an expected sequence by bitmap bits. Keep all 65,536 ordered byte pairs; force the *new* entry and repeat pairs in each half of a long enough run (the existing 64-byte tests would miss the ≥128 dispatcher). Exercise nonzero l/r, both exhausted-side directions, all-zero/all-one groups in mixed nodes, random symbols/masks, all alignments modulo 32, exact allocation ends, `n=0..129` and larger multiples ±1, set padding in the final byte. Compare with the bit cursor and actual child consumption. Test every suffix handoff including an early-depleted R followed by many all-left groups. For padded arms vary guard contents, surround the exact output with canaries, place the last legal read against a guard page or ASan redzone, and reuse buffers across successes/failures/frame-size changes. The same logical input must produce identical bytes with two unrelated guard patterns. A guard on wire input is never a precondition.
3. **Run the kernel discriminator.** Paired resident replay on CPU 3: A selected gather, B deposit, pinned C AVX2 gather with its own documented initialized slack. Also compare B/C with equivalent physical room, and record strict-window vs padded coverage; report padding/initialization costs at section level. Measure cycles **and instructions per gathered byte**, per-run latency by shape, plus total in-order weighted cost. Check actual code: two `pdep` per word, register masks/OR and qword stores; no helpers, stack-built windows, lane spills or unexpected bounds branches. For C-like Rust check two YMM shuffles, one blend, full store and actual loads. Fresh same-A and balanced shuffled pairs; a handful of uniform masks in L1 cannot decide. **Aim to halve the ~0.45 cycles/gathered-byte excess over C.** This is an ambition; judge against fresh paired numbers. If B cannot beat A on the original mix in cycles, or C decisively beats B there, stop tuning deposits and take #2 to section replay. If only the suffix loses and accounts for material volume, grant the guarded-source arm one comparison. If #2 loses too, retain A and price #3 by census.
4. **Make the whole decoder earn it.** Compare only the winning merge change to fresh A at the same pin; no simultaneous flat-six, compact-table, scratch schedule or SPL changes. Repeat original literal/token sections, checksum-verified `single`/`mozilla`/`sao` blocks and serial W1 through footer/EOF. Use the [paired protocol](../../doc/profiling/decode-compact0.sol.md): locked portable Release, no ledger/Tracy for timing, two independently shuffled 24-pair balanced series with same-A and separate C reference, pinned core, warmed bytes, grouped 100%-running user cycles/instructions plus thread CPU; report CLI wall MB/s, child CPU/GB, paired intervals, noise and hashes. W8 is secondary. Run exact plaintext/fingerprint and checksum-rejection preflights; preserve short/trailing run errors, invalid Kraft/depth/missing-child rejection, dictionary/inline behavior, block output limits and ordered verified publication. Run default and no-default, non-AVX fallback and scalar/explicit Wasm smoke (no timing necessary for smoke); include dense 4 KiB, RAW and `sao` controls. No ISA speed claim from emulation.

Promote a **smaller** reproducible checked-block/W1 saving if it is worth the code and causes no resolved control loss; 5% is not a minimum price of admission. A section-only win with unresolved W1 is precisely that. One quieter paired repeat can resolve an ambiguous result. Regressing checked decode, an unexplained skew/short control loss, or needing weaker validation falsifies this as the next shipping merge. This document selects the experiment; it reports no new timing.
