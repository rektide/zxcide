# Fast decode across independent frames

**Put the lifetime of compute resources under the decode operation; keep the lifetime of verification state at one frame.** My first Rust experiment would keep the existing bounded window, caller-owned I/O and footer barrier, but reuse the channel workers, their scratch, and the window's buffers. My second would let a regular-file caller give a worker a *position* instead of sending it a body the caller just read. Try the two switches independently on the same bytes. Neither a wider queue nor running independent frames concurrently is a prerequisite for either change.

Pool churn is real. A syscall trace on the archived eight-worker CLIs counted **96 Rust thread creations versus 9 C** for one bundle. But Rust has **no pool at one worker**, and C was already 2.04× faster on concat there. Eight-worker C does worker-local reads and has a separate ordered writer; its workers also do different work per decoded byte. I'd build the small engine experiment, not budget a 3× return for it. If it misses, move to the file path or block kernels according to the tests below.

## What the two engines promise

**C `5719a96f`.** The relevant code is [`src/cli/main.c`](https://github.com/hellobertrand/zxc/blob/5719a96f778226868b29dba621a8c4e302b74d7c/src/cli/main.c#L1776-L1864) and [`src/lib/zxc_driver.c`](https://github.com/hellobertrand/zxc/blob/5719a96f778226868b29dba621a8c4e302b74d7c/src/lib/zxc_driver.c), not `-b`, the seekable range API or the buffer API.

- `-qdc -T8 path` opens the file, requests 1 MiB stdio buffers, disables progress, passes stdout and a configured dctx to `zxc_stream_decompress`; default checksum verification is **on** outside benchmark mode (`main.c:442–445,2235–2237`). `driver.c:1345–1420` creates an engine **local to that call**. A second call on the same dctx is not a warmed thread pool. The header is parsed for every frame and a required dictionary checked against the single configured dictionary (`1190–1209`). Consecutive frames of the same block size and checksum-presence keep the engine; seek flag alone does not restart it. Incompatible ⇒ close, resync stdio position if positioned, start again (`870–876,1380–1403`).
- Caller admits work, `-TN` requests N workers, plus one writer, including at `-T1`. One bounded ring, a queue of slot IDs, output per slot. Four slots per worker for single-block jobs; two for batched jobs (`62–67,784–867`). Non-positioned input lives in the slots. POSIX regular file, wide `off_t`, successful `ftello`, >1 requested thread, block limit ≥64 KiB ⇒ use worker-local `pread` buffers; pipes do not qualify. Regular files with block limit <256 KiB can batch (separate condition; `zxc_internal.h:380`). These C7 frames are all 512 KiB, **one block per job**, 32 slots at eight workers. Caller reads block headers and for checked data can read the stored checksum with the next header, advances position over the body and folds trailer checksums (`897–987`). Worker re-reads the physical block by offset, revalidates header/extent, decodes, verifies the plaintext checksum with the frame-local index, and signals if at the write head (`462–491,509–595`; `zxc_decompress.c:1598–1655`).
- Writer waits for that head; only ordered write returns slot credit (`628–712`). **C drains every frame** (`878–888,1217–1237`). Local index starts at zero in `1016–1037`; reset digest, physical size and read-ahead; subtract writer base for this frame's plaintext size. Check EOF, any seek extent, footer and optional digest before reading next magic (`937–945,1103–1155,1403–1419`). Threads, scratch and ring can stay warm; no blocks from frame *i+1* overlap unfinished blocks of *i*. The writer's final buffered bytes may flush on the caller after join.

**Rust `956e0000`.** [`crates/cli/src/main.rs`](../../crates/cli/src/main.rs) lines 49–79, 147–153, 197–228 selects serial for one worker, otherwise Crossbeam by default with `min(2W,256)` slots; file type is erased behind `Box<dyn Read>`. Output is buffered stdout or a temporary file flushed and persisted without clobber on success. [`parallel/src/lib.rs`](../../crates/parallel/src/lib.rs) lines 109–155, 192–224 validates the config, reads a prologue, resolves a dictionary, calls `driver.run(next,work,commit)`, then finishes the frame. The driver object is already outside that loop; **moving its constructor does nothing**. [`channel.rs:124–224`](../../crates/parallel/src/channel.rs) constructs both bounded queues, all scoped threads, credit and pending vectors **inside `run`**. Each thread lazily constructs `BlockDecoder`; a checked worker panic becomes an ordered error and invalidates scratch. Even an empty frame runs the scope. Rayon differs: [one scoped pool per operation](../../crates/parallel/src/rayon.rs), but per-frame scratch/window, plus a barrier each batch. Comparing backends is not an isolated thread-lifetime experiment.

The coordinator takes a buffer **before** reading a header/body; it alone reads and writes. `read_data_block` parses bounds, `resize(len,0)` then `read_exact` for body plus checksum. For RAW, verified output reuses that body, excluding trailer; coded output swaps backing Vecs with the worker. Pending results hold credit until ordered commit. [`codec/src/frame.rs:223–335`](../../crates/codec/src/frame.rs) rejects an empty input/trailing junk; per-block commit checked-adds cumulative output, enforces the limit before `write_all`, and records the physical/logical sizes and verified checksum fold. On EOF `finish` consumes the announced seek extent based on plaintext length and block size, and compares the expected footer including digest. Sequential decode does not validate every seek-table entry. Serial `Decoder` already retains private body/codec buffers across frames. [`wire.rs:24–114`](../../crates/codec/src/wire.rs) binds each data header to frame settings, including an optional dictionary ID (zero is valid). [`block.rs:26–39,70–136`](../../crates/codec/src/block.rs) checks the dictionary and extent and fits Huffman scratch to the block limit. A physical buffer, a verified plaintext prefix and a permit to read another block are three different things.

## The first implementation experiment

Make a **private, decode-operation-scoped execution session**. Keep `decode(Read, Write, DecodeOptions, Config)` and its non-`Send` I/O on the caller. Use a scoped `with_workers(config, work, |session| …)` whose coordinator can drive a bounded sequence of frames. Reuse the channel sliding-window primitive for the one-frame path; no process-global pool, no per-job boxed closure, no need to make caller dictionaries `'static`. Keep the Rayon comparator and one-worker serial path honest. A persistent service across *calls* would change resource ownership/idle thread cost and would do nothing for separate CLI processes. It needs its own use case.

1. **Enter a frame.** Parse via `DecodeFrame::start`, resolve the dictionary once using existing validation semantics. A job can own `(frame_generation, local_index, validated DataBlockHeader, optional_dictionary_slot, body Vec)`; the immutable dictionary slice lives in the operation closure. A small helper can return the first matching dictionary slot rather than cloning its content/tree. Keep the channel's current `Send + 'static` payload bound; worker uses the slot in the borrowed slice and the codec still checks the ID. New settings/limit and cleared digest/disk/plain/index on *every* prologue. Separate ring sequence from checksum seed; after a drained window resetting both admission/commit counters per frame is enough. Use checked counters. Options and cumulative output are operation-local.
2. **Admit, compute, commit.** Keep `K` circulating credits. Free + reserved for read + admitted-uncommitted = `K`, including worker-local jobs, queued results, pending results and head being written. Both bounded queues may have capacity `K`; this is one shared window, not `K` blocks in each stage. Worker owns its reconstruction and entropy scratch, transfers `OwnedVerifiedBlock` on success; the sole coordinator holds pending by ordinal and writes the maximal contiguous verified prefix. Return the backing buffer/credit only after successful commit. **Repair the EOF credit:** today's `next(Vec) -> Option<Job>` consumes the popped buffer on `None`; that was harmless when the entire ring was dropped. Let next fill a lending reservation or return the unused Vec on EOF. Multiple empty frames must not shrink the available window to zero. No admission at all without a credit.
3. **Barrier and retention.** Drain all accepted jobs and verified writes, including pending errors in stream order; compare footer/seek extent on the caller, then start next frame. `Q::recv_job` sleeping across that interval is normal. Initial compatibility rule: retain resources across equal **block limits**; mismatched limit ends the resource epoch after drain and starts a fresh one (can defer creation until data). Checksum/seek/dictionary are job/frame state, not reasons for separate pools in Rust. Rebuilding on size change is a simple enforceable downshift policy for **idle** workers and unused slot buffers too. Inspect later whether explicit trim on downshift is cheaper. Re-arm the window only when every held result/credit has been accounted for. End of stream or error joins every worker and releases all buffers.
4. **Failure precedence.** Preserve `channel.rs:175–220`: source/framing failure is ordered *after* admitted jobs; first observed worker error stops further admissions but earliest failing position/commit wins. Footer follows the last successful block; no later frame may publish on a bad footer. `write_all` can leave a prefix of the failing **verified** block on an external sink. Preserve the original error; drop the session on failure. Keep `catch_unwind` around worker compute (including scratch initialization); produce an indexed error exactly once for its job, discard poisoned scratch. On spawn failure, disconnect or coordinator unwind, cancel, **close both coordinator endpoints before join** and ensure no retained sender/receiver can keep a blocked lane alive. If adding fallible code outside compute, provide a worker-loss notification that wakes the coordinator waiting for a missing head. No forced cancellation of synchronous external reads/writes; do not promise a timeout a generic `Read` cannot deliver.

The memory budget is `K` circulating block buffers + ≤`W` reconstruction buffers + private worker entropy scratch + bounded queues/metadata and transient codec allocations. Track **capacity** in the swap path, not just payload `len`; Vecs may overallocate. Three retained Huffman Vecs alone can reach `2B + floor(B/5)` per active worker (1,153,433 B at `B=512 KiB`; [measured retention](../../doc/profiling/pivco-worker.md#allocation-and-retention)). `K=16`, `W=8` at this block limit implies roughly 12 MiB for block-sized buffers plus up to 8.8 MiB of these entropy buffers **before** Vec growth, metadata, allocator, stacks and I/O. This is a scale estimate, not an RSS ceiling. Grow on demand, cap by validated frame sizes, retain nothing after return; never allocate `MAX_WORKERS × MAX_BLOCK` at session start. Measure aggregate peak *and* bytes retained at barriers; confirm no growth with frame count and the 2 MiB→4 KiB downshift with fewer jobs than workers.

### If the session is not the answer

**Positioned file input** is the first alternative supported by current supply traces. Add a file-capable entry point before erasing the file to `Read`. A logical forward cursor reads and validates each small header, checks `offset + physical_length` against the supplied stable file length using checked arithmetic, admits `(generation,index,header bytes,offset,extent)` on one credit. No whole-file index, seek table or archive-sized mmap required. Worker uses exact offset reads into private recyclable storage; reparse/compare the **same physical header** it measured before decoding any body, reject short/mutated extents. Fold the checksum from that worker's verified bytes in ordered commit; no need to duplicate C's separate trailer read-ahead. Use the logical cursor for EOF/seek extent/footer, validate exactly as the stream decoder does. A file modified underneath decode is not a snapshot; detect conflicting descriptors/truncation, don't claim protection against coherent rewrites without checksums. Restrict initial selection to stable regular files on a platform with true positional reads; for ambiguous capabilities, stdin/pipes/custom readers continue to work. [`seek/src/lib.rs:24–124`](../../crates/seek/src/lib.rs) already has a cursor-independent primitive; share the small abstraction if useful, not `Archive::open/copy_range` (requires indexed frames, different integrity contract). An immutable slice can send bounded ranges into borrowed storage via the enclosing scope, without reading through a `Cursor` into each job, if memory consumers warrant their own path. Charge any output copy introduced by that choice, especially RAW.

**Generic streaming or slow output.** Where serial input preparation is on-CPU, first try retaining initialized input extent and passing logical slices, with exact reads into valid initialized storage; do not use unchecked `set_len` to spare zeros. If output blocks the coordinator while there is unread work, a split reader/ordered writer can overlap those roles. In that variant each credit spans read **through write**, not result send. A Send-capable file/stream adapter could move the source to a scoped producer, leaving a non-`Send` writer on the caller; moving the writer instead has the symmetric constraint. Frame drain/validated footer needs an explicit acknowledgement before the producer advances, all waiters need shutdown, and a producer blocked in external I/O cannot be synchronously cancelled. Don't add `Send` to today's generic API or stage an entire frame to support it. For interactive streams, test a producer pausing after one block while output is wanted: a fill-first coordinator can wait on more input before collecting a ready head. Bound and measure first output with a progressing producer; genuinely independent delivery requires a split role or an incremental driving API.

**Worker CPU.** Attribute on-CPU cycles/instructions per plaintext byte in clean profiles, and per Huffman symbol/LZ sequence in separate diagnostic builds. Split out inline-tree build, flat unpack, mixed-node merge/copy-back, SPL16 inline/escape/overlap/tail, resize/zero-init, checksum. Map Rust `codec/src/entropy.rs:109ff`, `entropy/{flat,merge}.rs`, `block.rs:152–269,318–492`, `wire.rs:155–164` against C `zxc_huffman.c:2176–2321`, `zxc_decompress.c:805–1178,1598–1655`, ISA dispatch in `zxc_dispatch.c:318–408`. `webster`/`mozilla` weight sequence work; compare Huffman-heavy `sao` and matched raw-section Split, PAK and long RAW. If reconstruction dominates, specialize the measured token/overlap class with proven initialized source, destination room, dictionary and logical-prefix bounds. If entropy dominates, time compact level/run tables or flat unpack against the existing tree; previous queue/copy-back experiments missed elapsed gates. If hash/resize dominates, improve exactly that. Do not save CPU by disabling checksums or changing future encoder output. Check `target-cpu=native` and dispatch on/off as *attribution* controls; keep portable Release and scalar/WIT safety baselines for promotion.

**Cross-frame work stealing/lookahead** is a later, separate option for streams of tiny frames. Neither current C nor the proposed first Rust session needs it. A simple `Begin/Block/End` token stream doesn't solve locating the next footer: seek extent/footer widths depend on verified plaintext length, and the generic `Read` cannot rewind. Speculation would need trusted prevalidated spans or a bounded framing mechanism, separate frame-local ordered commit records and error fences, one global slot/byte limit including empty-frame metadata, and proof that a corrupt footer never releases later output. Try only if *after* warm-session reuse most loss is measured in repeated drain/refill shoulders, not in long-frame interiors. A larger window cannot accelerate a single slow final block.

## Decision and promotion gates

- **Baseline first.** Warm, locked, quiet Release runs; two independently ordered series of at least 24 adjacent balanced pairs on the same physical-core mask. Include A/A; record load, placement/SMT, clocks, cache policy, build flags/hashes and actual threads. First target 8 workers, original C7 concat; include 1, 4, 12 and separate/one-large controls. Confirm finalists on **1,2,3,4,6,8,12,16** and a real output path. Exact bytes/EOF, success/quiet stderr outside timing for every combination, errors checked in timing. Report paired wall, CPU s/GB, first-write and frame-completion latency (including p95), peak RSS and capacities, not winner over a noisy worker sweep. Trace thread CPU vs elapsed and sched switches for spawn/join, first scratch growth, header/read, verify and commit in separate runs; credits/empty-queue intersections and critical-path intervals, not a sum of overlapping stage ms.
- **Lifetime experiment.** Require 8 worker starts/one join group for the compatible corpus instead of 96, same `K=16`, every boundary drained, and capacity flat under repetition. Compare *both* persist-all and keep-threads/reset-storage at the same boundaries to distinguish memory reuse from thread reuse. Proposed ship screen: ≥5% less clean concat wall in both series, paired 95% interval excluding zero, ≤3% CPU cost increase. Treat it as a **main cause** only if it removes ≥half the *contemporaneous* Rust–C excess ms. If the upper bound on its benefit is <5% or the single-large-frame/replayed-block gap remains, stop attributing the gap to pool lifetime. A small, useful tiny-frame win can be a separate claim, not a reason to keep tuning the pool for Silesia.
- **Sustained speed.** For the file path require ≥10% less wall at 8 on both original concat and a large single frame, with feed-starvation/reader CPU reduced, ≤3% higher child CPU/GB, and no regression of the fallback. For a kernel candidate require ≥5% on checked block replay **and** ≥5% on its named fixed-archive end-to-end case. Recompute speed relative to C at the same count and percentage of excess ms removed; if ≥90% of C's contemporaneous throughput is not achieved, report the remaining gap. When noise intervals include useful gains and losses, result is unresolved, not promoted or falsified.
- **Latency/resources.** For every candidate, no repeatable >3% wall loss on separate, serial and single-frame controls; no >5% p95 first-write/frame-completion regression or >10% peak RSS increase at the same W/K absent an explicit deployment tradeoff. Use intervals and sufficiently many latency observations; don't decide tails on six/seven runs. Verify `slots=1`, `slots<W`, slow head/slow sink and huge→tiny→empty loops; show bounded held buffers/metadata under backpressure with no growth proportional to input/frame count. More threads or slots require their own budget.
- **Semantics.** Compare exact outputs and first error/verified prefix against serial for alternating checked/unchecked, seek/no-seek, dictionary A/B/none/ID-zero, wrong or missing dict on an empty frame, changing block limit, malformed EOF/seek/header/footer, corrupt late blocks racing earlier failures, cumulative max at/inside a boundary and writer partial write/flush failure. Test unwind, panic, partial spawn and cancellation during full queues with timeouts. Named-file failure must not publish; streaming output may have the earlier verified prefix. Extend [`parallel/tests/streaming.rs`](../../crates/parallel/tests/streaming.rs), [`scheduler_tests.rs`](../../crates/parallel/src/scheduler_tests.rs) and blocked-head/CLI tests; run workspace nextest with transports, pinned C interop, malformed vectors/fuzz regressions, scalar/component and indexed-range controls if shared codec/I/O changes.

The decision for review is whether to fund the small drained-session trial and the independent file-source comparison. They answer different questions and can land independently. If neither improves clean wall, use checked memory/block replay to select a codec change; do not spend another iteration on a larger queue without evidence that ordered backpressure is leaving compute capacity unused.
